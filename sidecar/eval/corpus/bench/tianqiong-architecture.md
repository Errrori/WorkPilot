# 天穹技术架构

## 服务划分

采集、存储、查询三层独立部署，灰度期间新旧集群双写。

## 数据与检索

- Markdown 分块约 800 字符/块、100 字符重叠，索引写入 Postgres pgvector。
- Kafka 使用 3 个 broker，ClickHouse 使用 3 个分片，热数据保留 30 天，冷数据保留 180 天。
- OpenTelemetry Collector 负责日志、指标和追踪接入，Grafana 提供统一查询入口。
- 平台日志使用结构化 JSON，查询与告警链路记录 trace_id、租户和耗时。

## 部署与回滚

采集、存储、查询三层独立部署，灰度期间新旧集群双写。

## 安全与权限

多租户通过租户 ID 和资源配额隔离，内测阶段使用平台组白名单。

## 可观测性

平台自身也接入 Prometheus，监控 Kafka 堆积、ClickHouse 磁盘和告警送达延迟。

## 容量与扩展

当前容量按试点规模设计，查询和写入都保留横向扩展空间。容量达到阈值时优先扩容存储和消费者，再考虑拆分服务。所有扩容操作必须更新风险台账和发布计划。

## 技术债

已知技术债包括监控覆盖不完整、部分脚本缺少自动化测试、灰度回滚依赖人工确认。技术债按季度评估，不阻塞当前迭代的功能交付。

## 模块边界

系统按接入、存储、查询、展示和任务调度划分模块。接入层只负责协议转换和鉴权，存储层负责数据生命周期，查询层负责检索和聚合，展示层不直接访问数据库。模块之间通过明确的接口通信，避免共享内部数据结构。

## 数据流

写入路径先进入消息队列，再由消费者落库；查询路径走缓存和索引，避免直接扫描全量数据。文档上传后先解析，再分块和向量化，最后写入索引。索引失败保留原文，支持手动重建。

## 容量估算

容量按试点规模的两倍设计，预留突发流量和索引重建空间。磁盘、连接数和消费者并发都设置预警阈值。达到阈值时先扩容，再评估是否需要拆分服务。容量变更需要同步风险台账。

## 故障演练

每季度至少进行一次故障演练，覆盖实例下线、队列堆积、数据库连接耗尽和索引不可用。演练记录恢复时间、影响范围和改进项。未通过演练的链路不能进入全量发布。

## 配置管理

所有配置通过环境变量注入，不在代码中硬编码连接串和密钥。本地开发使用样例配置，生产配置由部署平台管理。配置变更需要评审，并在发布计划中记录回滚值。
